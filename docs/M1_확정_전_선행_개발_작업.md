# M1 확정 전 선행 개발 작업

작성일: 2026-09-18

## 목적과 결론

서비스 범위·가격 비교 규칙(M1)을 지금 확정할 수 없어도 개발을 진행할 수 있다. **기존 실행 환경을 확인한 다음, API 공통 처리 → 모바일과 API 통신 확인 → 자동 검사 구성** 순서로 진행하는 것을 권장한다.

이 작업들은 카테고리, 대상 쇼핑몰, 상품 동일성, 배송비 계산, 인증 방식을 정하지 않아도 수행할 수 있다. 다만 M1·M2를 대체하지 않으며, 완료해도 실제 상품의 수집·비교가 검증되거나 M3 전체가 완료되는 것은 아니다.

이 문서는 로컬 `main`의 `0b7339c`를 기준으로 작성한 작업 제안이다. 최초 작성은 문서·코드 조사만 수행했고, 후속 검토에서는 pnpm 호출 방식과 Prisma validate/generate를 직접 확인했다. 설치·전체 빌드·실기기 실행은 이번 후속 검토에서 수행하지 않았다. 확인 범위는 §7에 기록했다. 아래 체크리스트는 앞으로 할 일이며 구현 완료 기록이 아니다.

후속 검토에서 확인한 기존 문서와 코드의 불일치는 다음과 같으며, 관련 원문서에도 반영했다.

- 랜딩은 기본 안내 수준이라는 기존 설명과 달리 소개 섹션들이 구현되어 있다. 개인정보 처리방침·이용약관은 여전히 준비 단계다. 화장품 문구만으로 M1 카테고리나 비교 기준이 확정됐다고 간주하지 않는다.
- 랜딩에는 Vercel 설정이 커밋되어 있다. API·Worker·MySQL의 배포 위치는 미정이다. Vercel Git 연동과 실제 프리뷰·운영 배포 상태는 설정 파일만으로 확인할 수 없다.
- 랜딩에는 CSS Modules, Pretendard, 디자인 토큰이 적용되어 있다. 모바일의 최종 스타일링 방식은 별도 결정 사항이다.
- Python 의존성 관리는 uv로 구성되어 있다. 스케줄 실행 주기·중복 방지·재시도 방식은 별도 미정 항목이다.

| 순서 | 작업 | M1 없이 가능한 이유 | 선행 조건 |

**첫 구현 단위는 T1을 추천한다.** 기존 `/health` 동작을 유지하면서 서버를 테스트 가능하게 만들고, 모바일에서 처리할 통신 오류 형식을 마련할 수 있다. T0에서 기존 환경 문제가 발견되면 먼저 해결한다.

## 3. 작업별 범위와 완료 기준

### T0. 개발 환경 재현·기존 검사 확인

할 일:

- [ ] [SETUP.md](../SETUP.md)에 따라 잠금 파일을 사용하는 JS·Python 설치 절차를 확인한다. `.npmrc` 등 저장소·사용자 설정, `pnpm store path`, 기존 `node_modules/.modules.yaml`의 store 경로를 대조한다. 별도 팀 설정이 없다면 기본 store를 기준으로 재현하고, 사용자별 절대 경로를 커밋하지 않는다.
- [ ] 새 환경에서 `pnpm install --frozen-lockfile`을 재현한다. 기존 환경에 store 불일치가 있으면 설정 통일·의존성 재설치 방식을 먼저 정한다. `CI=true`나 강제 삭제로 비대화형 설치 오류만 우회하지 않는다.
- [ ] pnpm이 PATH에 없는 환경에서는 바깥 실행뿐 아니라 내부에서 pnpm을 다시 호출하는 `db:validate` 등의 동작도 확인한다. Corepack 직접 호출과 npx 호출의 검증 결과를 구분한다.
- [ ] 아래 기존 명령을 실행하고 성공 여부와 필요한 환경 설정을 기록한다.
- [ ] API `/health`, 모바일 초기 화면, 랜딩 페이지의 기본 실행을 확인한다.
- [ ] 설치·실행 과정에서 발견한 문서 오류만 수정하고, 랜딩 구현·Vercel 설정·스타일링·uv의 현재 상태와 원문서 반영 내용을 확인한다.

```powershell
pnpm typecheck
pnpm lint
pnpm build
pnpm db:validate
uv run --project apps/crawler python apps/crawler/src/main.py
```

완료 기준:

- 다른 팀원이 같은 절차로 환경을 구성할 수 있고, 기존 검사의 결과가 기록되어 있다.
- 현재 설정의 Prisma validate/generate는 `DATABASE_URL`과 DB 접속 없이 통과함을 확인했다(§7). DB 연결과 마이그레이션 검증은 별도 작업이다.
- 모바일 웹 번들 성공을 Android·iOS 설치 및 실기기 검증 성공으로 기록하지 않는다.

이 단계에서 의존성 전체 업데이트, 프로젝트 재생성, 서비스용 테이블 생성은 필요하지 않다.

### T1. API 공통 처리와 동작 테스트

작업 위치: `apps/api/src/`, `packages/shared/src/schemas/`, 각 패키지의 `package.json`.

할 일:

- [ ] Express 앱 구성과 포트 실행을 분리한다. 예를 들어 `src/app.ts`는 앱을 구성하고 `src/index.ts`는 설정을 읽어 서버를 시작한다.
- [ ] `PORT`를 검증해 잘못된 값일 때 원인을 명확히 표시한다. `/health`만 실행할 때는 DB 접속을 필수로 만들지 않는다.
- [ ] 존재하지 않는 경로, 잘못된 JSON 요청, 예상하지 못한 서버 오류에 대한 JSON 응답을 일관되게 처리한다.
- [ ] API와 모바일이 함께 사용할 최소 오류 형식과 기존 health 응답의 검증 스키마를 shared에 정의한다. 오류 형식은 `error.code`, `error.message` 정도부터 검토한다.
- [ ] 서버 내부 오류의 스택·접속 정보가 응답에 포함되지 않도록 처리한다.
- [ ] 실제 요청·응답을 검증하는 API 테스트와 실행 명령을 추가한다.

완료 기준:

- `GET /health`가 기존과 같이 200 및 `{ "status": "ok" }`를 반환한다.
- 없는 경로는 404, 잘못된 JSON은 400, 예상하지 못한 오류는 500으로 처리되고 정한 오류 형식을 따른다.
- 500 동작은 테스트에서 오류를 주입해 검증한다. 서비스에 오류 발생용 공개 경로를 추가하지 않는다.
- 테스트가 DB·쇼핑몰·고정 개발 포트에 의존하지 않는다.
- 기존 build/typecheck가 통과하고 추가된 API 테스트를 한 명령으로 실행할 수 있다.

범위 제한: 인증, 권한, 상품 검증, 가격 계산, Worker 내부 API를 구현하지 않는다. 모든 성공 응답을 감싸는 범용 응답 구조나 복잡한 오류 체계도 미리 만들 필요가 없다.

### T2. 모바일 API 클라이언트와 `/health` 연결

작업 위치: `apps/mobile/lib/api/`, `apps/mobile/.env.example` 신규 파일, 개발용 확인 화면, shared의 health·오류 스키마.

할 일:

- [ ] 공개 가능한 API 기본 주소를 환경 설정으로 분리한다. 예: `EXPO_PUBLIC_API_URL`. 모바일 설정에는 비밀값을 넣지 않는다.
- [ ] 기존 `fetch`를 중심으로 필요한 최소 요청 함수를 만든다. JSON 읽기, HTTP 오류, 네트워크 실패, 타임아웃을 처리한다.
- [ ] shared의 health 응답 스키마로 서버 응답 형태를 확인한다.
- [ ] 개발 중에만 사용하는 확인 화면에서 `/health`를 호출하고 로딩·성공·실패·재시도 상태를 확인한다.
- [ ] PC, 에뮬레이터, 실기기에서 사용할 주소와 로컬 네트워크 설정을 실행 안내에 기록한다. 실기기에서 PC 서버를 호출할 때 기기 자신의 `localhost`를 사용하지 않도록 안내한다.

완료 기준:

- 실행 가능한 모바일 환경 한 곳 이상에서 API 성공 응답을 확인하고, 사용한 기기·실행 방식을 기록한다.
- 서버를 끄거나 잘못된 주소를 설정했을 때 앱이 종료되지 않고 오류와 수동 재시도 동작을 제공한다.
- 서버 복구 후 재시도로 성공 상태에 도달한다.
- 타임아웃과 잘못된 응답 처리는 통제된 테스트 응답으로 확인한다.
- 개발용 서버 상태·주소가 일반 사용자 화면에 상시 노출되지 않는다.

범위 제한: 상품 더미 데이터를 실제 API 계약으로 고정하지 않는다. 자동 재시도 정책, 토큰 갱신, 로그인 상태 관리는 필요한 정책이 정해진 뒤 추가한다. Expo 웹도 확인하려면 개발용 출처 허용 설정을 별도로 검토한다.

### T3. GitHub Actions 검사 구성

작업 위치: `.github/workflows/` 신규 파일, 루트 `package.json`, `turbo.json`.

할 일:

- [ ] PR에서 기존 typecheck/lint/build/Prisma 스키마 검사를 실행하도록 구성한다.
- [ ] 저장소가 지정한 pnpm 버전과 잠금 파일을 사용한다. Python 환경도 uv와 `uv.lock`으로 재현한다.
- [ ] T1 완료 후 API 테스트를 자동 검사에 추가한다. 그 전에는 기존 검사만 자동화할 수 있다. 루트에 test 명령을 추가한다면 Turborepo 작업과 연결한다.
- [ ] 기존 Vercel Git 연동·프리뷰 빌드가 활성화되어 있는지 확인하고, Vercel의 랜딩 배포 검사와 GitHub Actions의 저장소 품질 검사를 구분한다. 겹치는 랜딩 빌드를 유지할지 검토하고 각 결과의 의미를 기록한다.
- [ ] Python은 현재 가능한 설치·구문 검사부터 포함한다. 실제 수집·파싱 기능이 생기면 의미 있는 테스트를 추가한다.
- [ ] 실패한 작업을 PR에서 식별할 수 있도록 검사 결과를 확인한다.

완료 기준:

- 깨끗한 CI 환경에서 잠금 파일 기반 설치와 검사가 성공한다.
- T1 테스트를 포함한 뒤에는 실제 API 동작을 깨뜨리는 임시 변경에서 테스트가 실패하는지 확인하고, 임시 변경을 제거한다.
- 운영 DB, 쇼핑몰 자격 증명, 배포 토큰 없이 기본 검사가 동작한다.
- 현재 Prisma validate/generate 검사에는 더미 `DATABASE_URL`이나 DB 서비스를 추가하지 않는다. 연결·마이그레이션 테스트를 추가할 때 필요한 DB 설정은 별도로 마련한다.

범위 제한: 자동 배포 신설·변경과 브랜치 보호 설정 변경은 포함하지 않는다. 기존 Vercel 빌드와 GitHub Actions의 역할 구분은 포함한다. CI 파일 작성과 실제 GitHub 실행 확인은 별개이며, PR 실행 전에는 검증 완료로 표시하지 않는다.

### T4. 린트 범위 확장

작업 위치: `apps/api`, `apps/mobile`, `packages/shared`, `packages/db`의 ESLint 설정·실행 명령, 필요 시 루트 공통 설정.

할 일:

- [ ] 랜딩 외 TypeScript 코드도 lint 대상에 포함한다.
- [ ] Node 서버와 Expo·React 환경에 맞는 최소 규칙을 적용하고, 모바일에는 React Hooks 관련 검사를 포함한다.
- [ ] Prisma 생성 코드·빌드 결과·캐시를 검사 대상에서 제외한다.
- [ ] 필요한 오류만 수정하고 기존 코드 전체의 스타일 변경은 별도 작업으로 분리한다.

완료 기준:

- 루트 `pnpm lint`가 API·모바일·shared·DB·랜딩의 작성 코드를 검사한다.
- 생성 파일 때문에 불필요한 오류가 발생하지 않고 T3의 CI에서도 같은 검사가 실행된다.

## 4. 필요할 때만 추가할 수 있는 작업

**로컬 MySQL 연결 확인:** T0~T2 이후 DB 실행 환경을 미리 준비할 필요가 있다면 개발용 DB 기동 절차, 예시 환경 변수, 기존 `createDbClient()`를 이용한 연결 확인과 종료 처리를 추가할 수 있다. 상품 테이블 없이 연결 여부만 검증하고, 상품·가격 이력 모델과 첫 서비스 마이그레이션은 M2 결과 이후로 둔다. 로컬 실행 방식을 운영 배포 플랫폼 결정으로 간주하지 않는다.

**기기 실행 점검:** 확보된 Android·iOS 기기에서 현재 앱의 실행·화면 이동을 확인하고 결과를 기록할 수 있다. 기기, 계정, 빌드 환경이 필요한 작업은 준비 상태를 먼저 확인한다. 푸시 제공 방식이나 계정 정책을 임의로 확정하지 않는다.

## 5. M1·M2 또는 별도 결정 이후에 진행할 작업

| 보류할 작업 | 필요한 결정·검증 |
|---|---|
| 특정 쇼핑몰 수집기·HTML 파서 구현 | 대상 쇼핑몰, 접근 방법, 실제 응답, 데이터 사용 조건 |
| 상품·옵션·판매 정보·가격 이력 DB 모델 | 실제 데이터 필드와 동일 상품·비교 기준 |
| 가격 합산·정렬·품절·오래된 가격 판정 | 배송비·옵션·신선도 등 서비스 규칙 |
| 로그인·회원가입·관심 상품 저장 방식 | 계정 필요 여부, 기기 간 동기화 범위 |
| Worker 내부 API 또는 DB 직접 저장 | 저장 경로와 권한·검증·실패 처리 설계 |
| 수집 스케줄·재시도·중복 방지의 본 구현 | 제공처 제한, 실행 주기, 저장 단위 |
| 목표 가격 알림·제휴 링크·광고 | 가격 판정, 사용자 식별, 제공처·수익화 정책 |
| 상품 UI·랜딩 문구의 서비스 약속 확정 | 실제 제공할 기능과 데이터 범위 |
| API·Worker·MySQL 배포 및 운영 구성 | 배포 위치·비용·비밀값·백업·운영 권한. 랜딩의 기존 Vercel 설정과 구분 |

현재 `coupang.py`, `gmarket.py`, 로그인 화면, 내부 Worker 라우터가 존재한다는 이유만으로 해당 선택이 확정된 것은 아니다.

`apps/landing/vercel.json`은 랜딩의 배포 설정이며 API·Worker·MySQL 배포 위치까지 확정한다는 뜻이 아니다. 랜딩의 CSS Modules 사용도 모바일 스타일링 방식의 확정을 뜻하지 않는다.

## 6. 권장 작업 묶음

1. **기존 상태 확인:** T0 결과와 문서의 상태 차이를 기록한다.
2. **첫 개발 PR:** T1의 API 구성 분리·설정 검증·공통 오류 처리·health/오류 스키마·동작 테스트를 묶는다.
3. **통신 확인 PR:** T2의 최소 API 클라이언트와 개발용 `/health` 연결 확인을 묶는다.
4. **자동 검사 PR:** T3를 적용한다. 기존 검사만 자동화하는 부분은 T1·T2 완료 전에도 진행할 수 있다.
5. **검사 범위 확대 PR:** T4를 적용하고 CI에 반영한다.

이후 M1을 진행할 수 있게 되면 기존 마일스톤의 **범위 확정 → 실제 데이터 검증 → 상품 하나의 전체 연결** 순서로 돌아간다.

## 7. 후속 검토 기록

2026-09-18 기준. 사용자 제공 실행 결과와 이번 직접 확인을 구분한다.

| 항목 | 확인 결과 |
|---|---|
| T0 명령 5개 | 사용자 검토에서 모두 성공했다고 보고했다. 이번 후속 검토에서는 전체를 재실행하지 않았다. |
| pnpm store | 저장소·홈의 `.npmrc`는 없고 기본 store는 `%LOCALAPPDATA%/pnpm/store/v10`이다. 기존 `.modules.yaml`에는 저장소의 `.pnpm-store/v10`이 기록되어 있어 불일치를 직접 확인했다. |
| 설치 실패 | `ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY`는 사용자 검토에서 보고한 결과다. 기존 의존성을 재구성할 수 있는 install은 이번에 재실행하지 않았다. 새 체크아웃의 설치 실패까지 의미하지 않는다. |
| pnpm 호출 | PATH에 pnpm이 없는 상태에서 `corepack pnpm db:validate`는 내부 pnpm을 찾지 못해 실패했다. `npx --yes pnpm@10.34.5 db:validate`와 offline 호출은 모두 성공했다. npx도 항상 실패한다는 주장은 이번 환경에서 재현되지 않았다. |
| 중첩 호출 범위 | `db:validate`, `db:generate`, `dev:mobile`, `dev:api`, `dev:landing`은 내부에서 pnpm을 호출한다. `dev:crawler`는 uv를 직접 호출한다. |
| Prisma | `packages/db/.env`가 없는 상태에서 프로세스의 `DATABASE_URL`을 제거하고 로컬 Prisma 실행 파일로 validate/generate를 실행해 모두 성공했다. 설정 파일 조사만으로 추정한 결론이 아니다. |
| 원격 상태 | Vercel Git 연동·실제 배포·GitHub Actions 실행은 확인하지 않았다. 로컬 원격 추적 브랜치와의 일치는 원격 서버 최신 상태의 확인을 뜻하지 않는다. |

이 문서 수정만으로 store 불일치나 PATH 설정이 해결된 것은 아니다. T0에서 환경 재현을 마무리한 뒤 T1을 진행한다.
