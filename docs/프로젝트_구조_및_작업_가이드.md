## 1. 전체 구조와 데이터 흐름

`apps/`는 독립적으로 실행하는 프로그램, `packages/`는 프로그램에서 가져다 쓰는 공통 코드를 보관합니다. 각 `src/`는 해당 프로젝트의 소스 코드 위치입니다.

```text
De.O/
├── apps/
│   ├── mobile/       Expo 모바일 앱
│   ├── api/          Express API 서버
│   ├── crawler/      Python 수집 Worker
│   └── landing/      Next.js 소개 웹사이트
├── packages/
│   ├── db/           Prisma 설정·DB 스키마·클라이언트
│   └── shared/       모바일·API 공통 데이터 규칙
├── docs/             개발 계획과 작업 안내
├── package.json
├── pnpm-workspace.yaml
├── pnpm-lock.yaml
├── turbo.json
├── tsconfig.base.json
├── README.md
└── SETUP.md
```

목표로 하는 조회 흐름은 다음과 같습니다. 현재 상품 조회와 DB 연결까지 구현된 상태는 아닙니다.

```text
사용자 → mobile → api → packages/db의 Prisma 클라이언트 → MySQL
          └──────── packages/shared의 데이터 규칙 ────────┘

crawler → 수집 → 데이터 정리 → 저장 경로는 M3에서 결정
landing → 앱 소개·사용 안내·다운로드 안내
```

- 모바일은 API를 통해 데이터를 조회합니다. DB 접속 정보는 모바일에 넣지 않습니다.
- API와 Worker는 별도 프로세스입니다. 앱 조회 요청마다 쇼핑몰을 즉시 수집하는 구조로 만들지 않습니다.
- Worker의 저장 경로는 내부 API 전달 또는 DB 직접 저장 중 추후 결정합니다.
- 인증 방식, 대상 쇼핑몰, 가격 비교 기준 등 미정 항목은 [개발 마일스톤](최저가비교앱_개발_마일스톤.md)을 따릅니다.

## 2. 모바일 앱 — apps/mobile

사용자가 상품을 검색하고 가격을 확인하며 알림을 설정하는 곳입니다. 현재 화면과 이동 구조의 골격이 있고, 기능별 폴더는 대부분 비어 있습니다.

### 화면과 경로

아래 경로는 `apps/mobile/` 기준입니다.

| 폴더·파일 | 역할 | 앞으로 할 작업 |
|---|---|---|
| `app/` | Expo Router의 화면 경로 | 기능별 코드를 가져와 실제 화면 구성 |
| `app/_layout.tsx` | 앱 전체 화면 이동 구조 | 인증 상태와 화면 이동 정책 확정 후 반영 |
| `app/(auth)/_layout.tsx` | 로그인·회원가입 화면 묶음의 이동 설정 | 인증 화면의 제목·전환 동작 조정 |
| `app/(auth)/login.tsx` | 로그인 화면 | 인증 방식 확정 후 입력·검증·로그인 요청 연결 |
| `app/(auth)/signup.tsx` | 회원가입 화면 | 회원가입 필요 여부와 가입 절차 확정 후 구현 |
| `app/(tabs)/_layout.tsx` | 하단 탭 구성 | 탭 아이콘·표시 방식과 이동 동작 정리 |
| `app/(tabs)/index.tsx` | 홈 화면 | 홈에 보여줄 상품과 안내 구성 |
| `app/(tabs)/search.tsx` | 상품 검색 화면 | 검색 입력·결과·로딩·빈 결과·오류 표시 |
| `app/(tabs)/alerts.tsx` | 가격 알림 관리 화면 | 목표 가격 설정·알림 목록·해제 기능 연결 |
| `app/(tabs)/my.tsx` | 마이페이지 | 이용 방식에 맞춘 관심 상품·사용자 설정 구성 |
| `app/product/[id].tsx` | 상품 ID별 상세 화면 | 상품 정보·판매처별 가격·가격 추이·판매처 이동 구현 |
| `app/+not-found.tsx` | 없는 경로에 대한 안내 | 잘못된 주소에서 복귀하는 동작 확인 |
| `app/+html.tsx` | 웹 실행 시 HTML 문서 설정 | 웹에서 필요한 언어·메타 정보 점검 |

`(auth)`, `(tabs)`는 URL에 포함되지 않는 화면 그룹입니다. `[id]`는 상품마다 달라지는 ID를 받는 경로입니다. `_layout.tsx`는 화면 자체보다 화면들을 배치하고 이동시키는 설정을 담당합니다.

### 기능·공통 코드·설정

| 폴더·파일 | 역할 | 앞으로 할 작업 |
|---|---|---|
| `components/` | 여러 화면에서 재사용하는 UI | 공통 버튼·입력창·로딩·오류 안내 등을 필요할 때 추가 |
| `components/PlaceholderScreen.tsx` | 현재의 준비 중 안내 화면 | 실제 화면을 구현하면서 사용처 교체 |
| `features/auth/` | 인증 기능에 속하는 UI와 상태 | 로그인 상태·로그아웃 흐름 구현 |
| `features/products/` | 상품 기능에 속하는 코드 | 상품 목록·상세 표시·관심 상품 동작 구현 |
| `features/search/` | 검색 기능에 속하는 코드 | 검색 조건·결과 목록·검색 상태 구현 |
| `features/price-history/` | 가격 이력 표시 기능 | 실제 가격 기록을 사용하는 차트와 기간 선택 구현 |
| `features/price-alerts/` | 목표 가격 알림 설정 기능 | 목표 가격 입력·설정 저장·수정·해제 구현 |
| `features/notifications/` | 기기의 알림 수신 기능 | 알림 권한·푸시 토큰·알림 클릭 시 상세 이동 구현 |
| `hooks/` | 여러 화면에서 재사용하는 React 훅 | 반복되는 상태·동작이 생기면 공통 훅으로 분리 |
| `lib/api/` | 서버 통신의 공통 처리 | API 주소·요청 함수·공통 오류 처리 작성 |
| `lib/auth/` | 인증 관련 기반 처리 | 선택한 인증 방식에 맞춰 토큰·세션 처리 작성 |
| `lib/storage/` | 기기 내부 데이터 저장 | 설정·관심 상품 등의 로컬 저장 범위 확정 후 구현 |
| `assets/images/` | 아이콘·스플래시·이미지 | 앱 디자인 확정 후 기본 이미지 교체 |
| `assets/fonts/` | 글꼴 파일 | 사용 글꼴 확정 후 필요한 파일 관리 |
| `app.json` | Expo 앱 이름·아이콘·플러그인 등 설정 | 플랫폼 식별자·권한·출시 설정을 필요 시 추가 |
| `package.json` | 모바일 의존성과 실행 명령 | 기능에 필요한 라이브러리와 명령 관리 |
| `tsconfig.json` | TypeScript 검사와 경로 별칭 | 기존 설정을 사용하고 필요할 때 조정 |
| `.vscode/settings.json`, `.vscode/extensions.json` | 모바일 개발용 편집기 설정·권장 확장 | 팀 개발 환경에 맞춰 조정 |
| `.gitignore` | 모바일 생성 파일 제외 규칙 | 새 생성물이 생기면 규칙 점검 |
| `LICENSE` | 가져온 템플릿의 라이선스 고지 | 템플릿 코드 사용 시 고지 유지 |

**배치 예시:** `app/(tabs)/search.tsx`가 화면을 구성하고, `features/search/`가 검색 기능을 담당하며, `lib/api/`가 공통 통신을 처리합니다. 기능 하나에서만 쓰는 코드는 우선 해당 `features/` 폴더에 두면 됩니다.

## 3. API 서버 — apps/api

모바일 요청을 받아 검증하고, 서비스 규칙을 적용한 뒤 결과를 반환합니다. 현재 기능 라우터는 비어 있으며 `/health`만 응답합니다.

아래 경로는 `apps/api/` 기준입니다.

| 폴더·파일 | 역할 | 앞으로 할 작업 |
|---|---|---|
| `src/index.ts` | Express 서버 시작·라우터 연결 | 구현한 라우터와 공통 미들웨어 연결 |
| `src/routes/` | 요청 URL·HTTP 메서드와 처리 함수 연결 | 기능별 API 경로 정의 |
| `src/routes/auth.ts` | 인증 관련 API 경로 | 인증 방식 확정 후 로그인·가입·로그아웃 등 연결 |
| `src/routes/products.ts` | 상품 관련 API 경로 | 상품 목록·상세 조회 연결 |
| `src/routes/search.ts` | 검색 API 경로 | 검색 조건 검증과 결과 반환 연결 |
| `src/routes/prices.ts` | 가격 관련 API 경로 | 판매처별 가격·가격 이력 조회 연결 |
| `src/routes/alerts.ts` | 가격 알림 API 경로 | 알림 조건 등록·조회·수정·삭제 연결 |
| `src/routes/users.ts` | 사용자 관련 API 경로 | 확정된 사용자·관심 상품·설정 관리 범위 연결 |
| `src/routes/internal/crawler.ts` | Worker 전용 내부 API 후보 | 내부 API 저장 방식을 선택한 경우 인증·검증·수집 결과 수신 구현 |
| `src/controllers/` | 요청값을 받고 서비스 호출 후 응답 작성 | 상태 코드·응답 형식·입력 검증 연결 |
| `src/services/` | 업무 규칙과 처리 순서 | 비교 가격 계산·오래된 가격 처리·알림 조건 판정 등 구현 |
| `src/repositories/` | DB 조회·저장 코드 | Prisma를 이용한 상품·가격·알림 데이터 접근 구현 |
| `src/middleware/` | 여러 요청에 적용할 공통 처리 | 인증 확인·공통 오류 처리 등을 추가 |
| `src/utils/` | 서버의 작은 공통 보조 함수 | 실제로 반복되는 함수를 필요할 때 분리 |
| `.env.example` | 포트·DB 연결 환경 변수 예시 | 필요한 변수 이름과 안전한 예시값 관리 |
| `package.json` | API 의존성과 실행·빌드 명령 | 서버 기능에 필요한 의존성과 명령 관리 |
| `tsconfig.json` | 서버 TypeScript 컴파일 설정 | `src/` 코드를 `dist/`로 빌드하는 설정 유지 |

일반적인 요청 처리 순서는 다음과 같습니다. 각 계층은 기능을 개발하면서 필요한 만큼 추가합니다.

```text
routes → controllers → services → repositories → Prisma → MySQL
```

`internal/crawler.ts`는 현재 서버에 연결되어 있지 않습니다. 파일이 있다는 이유만으로 Worker가 데이터를 전송하거나 저장할 수 있는 것은 아닙니다.

## 4. 수집 Worker — apps/crawler

쇼핑몰에서 상품·가격 정보를 가져오고 정리하는 Python 프로그램입니다. 현재 `main.py`는 준비 상태를 출력한 뒤 종료하며, 나머지 Python 파일에는 역할 설명만 있습니다.

아래 경로는 `apps/crawler/` 기준입니다.

| 폴더·파일 | 역할 | 앞으로 할 작업 |
|---|---|---|
| `src/main.py` | Worker 실행 시작점 | 확정된 작업 실행 방식 연결 |
| `src/crawlers/` | 쇼핑몰별 데이터 수집 | 실제 데이터 확보 가능성 확인 후 수집 방식 구현 |
| `src/crawlers/base.py` | 수집기의 공통 인터페이스 위치 | 검증된 데이터 형식을 바탕으로 공통 입출력 정의 |
| `src/crawlers/coupang.py` | 쇼핑몰별 수집기 자리 표시자 | 대상 쇼핑몰로 확정된 경우 해당 수집기 구현 |
| `src/crawlers/gmarket.py` | 쇼핑몰별 수집기 자리 표시자 | 대상 쇼핑몰로 확정된 경우 해당 수집기 구현 |
| `src/parsers/` | 응답 데이터 해석·정리 | HTML·JSON에서 상품명·옵션·가격·배송비 등 추출 |
| `src/jobs/crawl_product.py` | 상품 수집 작업의 진행 순서 | 대상 선택 → 수집 → 검증 → 저장 흐름 구현 |
| `src/jobs/update_prices.py` | 가격 갱신 작업의 진행 순서 | 주기적 가격 갱신·이력 기록·실패 처리 구현 |
| `src/scheduler/` | 작업 실행 시점과 반복 관리 | 주기·중복 실행 방지·재시도 방식 확정 후 구현 |
| `src/clients/api_client.py` | 내부 API 통신 코드 위치 | 내부 API 저장 방식을 선택하면 인증·전송·오류 처리 작성 |
| `tests/` | 수집·파싱 결과 검증 | 응답 샘플로 가격·배송비·누락 필드·실패 상황 검사 |
| `pyproject.toml` | Python 버전 범위·프로젝트 의존성 | 필요한 의존성과 도구 설정 관리 |
| `uv.lock` | Python 의존성 버전 고정 | 의존성 변경 시 uv로 갱신하고 함께 관리 |

`coupang.py`, `gmarket.py`는 아키텍처 그림에 맞춘 파일명입니다. 대상 쇼핑몰이나 수집 방법이 확정된 것은 아닙니다. Worker의 저장 경로도 M3에서 결정합니다.

## 5. 소개 웹사이트 — apps/landing

앱의 기능과 사용 방법을 소개하고 다운로드를 안내하는 Next.js 웹사이트입니다. 현재 Hero·기능 소개·사용 흐름·FAQ 등 소개 섹션과 화장품 예시가 구현되어 있습니다. 개인정보 처리방침·이용약관은 준비 단계 안내이며, 실제 서비스 범위 확정을 대신하지 않습니다. 스타일은 CSS Modules·전역 디자인 토큰과 Pretendard를 사용하고, 랜딩용 Vercel 배포 설정이 반영되어 있습니다. 실제 Git 연동·배포 상태는 별도 확인 대상입니다.

## 6. DB 공통 패키지 — packages/db

저장할 데이터의 구조와 Prisma 클라이언트를 관리하는 서버 전용 패키지입니다. MySQL 설정과 클라이언트 생성 함수는 있지만, 아직 데이터 모델과 마이그레이션은 없습니다.

아래 경로는 `packages/db/` 기준입니다.

| 폴더·파일 | 역할 | 앞으로 할 작업 |
|---|---|---|
| `prisma/schema.prisma` | DB 테이블·필드·관계 정의 | 실제 수집 데이터를 확인한 뒤 상품·판매 정보·가격 이력·알림 모델 설계 |
| `prisma/migrations/` | DB 구조 변경 이력 | 모델 확정 후 Prisma 명령으로 마이그레이션 생성·관리 |
| `prisma.config.ts` | Prisma CLI의 스키마·마이그레이션 경로와 연결 설정 | 개발·운영 환경의 설정 방식 관리 |
| `src/client.ts` | `createDbClient()` 제공 | API에서 필요한 시점에 클라이언트 생성·사용·종료 연결 |
| `src/generated/prisma/` | Prisma가 생성하는 클라이언트 코드 | 직접 수정하지 않고 `pnpm db:generate`로 갱신 |
| `.env.example` | `DATABASE_URL` 형식 예시 | 실제 비밀값 없이 필요한 환경 변수 안내 |
| `package.json` | DB 의존성·생성·검증·마이그레이션 명령 | Prisma와 DB 어댑터 의존성 관리 |
| `tsconfig.json` | DB 패키지 컴파일 설정 | 생성 코드와 클라이언트를 빌드하는 설정 유지 |

`schema.prisma`를 변경하는 것과 실제 MySQL 구조를 변경하는 것은 별개입니다. 모델과 DB 연결을 준비한 뒤 마이그레이션을 적용하고, 클라이언트 코드를 다시 생성합니다. 구체적인 명령은 [SETUP.md의 DB 안내](../SETUP.md#환경-변수와-db)를 참고하세요.

## 7. 모바일·API 공통 계약 — packages/shared

모바일과 API가 같은 요청·응답 형태를 사용하도록 공통 규칙을 관리합니다. 현재 API 경로 접두사만 정의되어 있고, 스키마 파일은 자리 표시자입니다.

아래 경로는 `packages/shared/` 기준입니다.

| 폴더·파일 | 역할 | 앞으로 할 작업 |
|---|---|---|
| `src/schemas/` | Zod 기반 데이터 검증 규칙 | 기능별 요청·응답 형태와 입력 제한 정의 |
| `src/schemas/auth.ts` | 인증 관련 데이터 규칙 | 인증 방식 확정 후 요청·응답 스키마 작성 |
| `src/schemas/product.ts` | 상품 관련 데이터 규칙 | 상품 목록·상세 응답과 필요한 입력 스키마 작성 |
| `src/schemas/price.ts` | 가격 관련 데이터 규칙 | 가격·배송비·수집 시점·누락값 표현 방식 정의 |
| `src/schemas/alert.ts` | 알림 관련 데이터 규칙 | 목표 가격·설정 상태·등록 요청 등 정의 |
| `src/types/` | 공통 TypeScript 타입 | 필요한 공통 타입 작성. Zod에서 추론 가능한 타입은 중복 정의하지 않기 |
| `src/routes/index.ts` | API 경로 상수 | 현재 접두사를 기준으로 API 경로 변경 시 함께 갱신 |
| `src/constants/` | 양쪽에서 사용하는 상수 | 공통 제한값·상태값을 필요할 때 추가 |
| `src/index.ts` | 패키지 외부로 공개하는 항목 | 완성한 스키마·타입·상수를 내보내기 |
| `package.json` | 공통 패키지 의존성과 공개 경로 | Zod·빌드 설정과 exports 관리 |
| `tsconfig.json` | 공통 코드 컴파일 설정 | JS 코드와 타입 선언 생성 설정 유지 |

**DB 스키마는 ‘어떻게 저장할지’, shared 스키마는 ‘어떤 데이터를 주고받을지’를 정의합니다.** DB 모델을 그대로 API 응답으로 노출할 필요는 없습니다. shared에는 DB 접속 정보나 서버 비밀키를 넣지 않습니다.

| 폴더·파일 | 역할 | 앞으로 할 작업 |

| `turbo.json` | 작업 순서·캐시·빌드 결과 경로 | 새 작업과 출력 경로가 생기면 반영 |
| `tsconfig.base.json` | API·공유 패키지 등의 공통 TypeScript 설정 | 공통 설정과 앱별 설정을 구분해 관리 |

| `.vercelignore` | 랜딩 Vercel 배포에서 제외할 파일 | workspace·잠금 파일은 포함하고 로컬 생성물·비밀값은 제외 |
| `README.md` | 프로젝트 개요와 문서 진입점 | 실제 기능·개발 현황에 맞춰 갱신 |
| `SETUP.md` | 환경 준비·설치·실행·검증 방법 | 실행 절차나 환경 변수가 바뀌면 갱신 |

앱별 `package.json`은 해당 앱의 의존성과 명령을, 루트 `package.json`은 여러 프로젝트를 함께 실행하는 명령을 관리합니다. Python Worker의 의존성은 pnpm 대신 uv로 관리합니다.

## 9. 자동 생성 파일과 빈 폴더

아래 항목은 설치·실행·빌드 후 보일 수 있습니다.

| 항목 | 의미 | 다루는 방법 |
|---|---|---|
| `.gitkeep` | 비어 있는 폴더를 Git에서 유지하기 위한 표시 | 실제 파일을 추가하면 제거해도 됨 |
| `node_modules/` | 설치된 JS 라이브러리 | 직접 수정하지 않고 pnpm으로 관리 |
| `apps/crawler/.venv/` | Python 가상환경 | uv로 관리하며 직접 소스 코드를 작성하지 않음 |
| `dist/` | 컴파일·번들 결과 | 원본 소스를 수정한 뒤 다시 빌드 |
| `.next/` | Next.js 생성 파일 | 직접 수정하지 않음 |
| `.expo/`, `expo-env.d.ts` | Expo 로컬 정보·생성 타입 | 도구가 관리하도록 두기 |
| `next-env.d.ts` | Next.js 생성 타입 참조 | 직접 수정하지 않음 |
| `packages/db/src/generated/` | Prisma 생성 코드 | Prisma 생성 명령으로 갱신 |
| `.turbo/`, `.cache/`, `.pnpm-store/` | 작업·도구·의존성 캐시 | 소스 코드와 구분하며 Git에 포함하지 않음 |
| `*.tsbuildinfo`, `__pycache__/` | TypeScript·Python 캐시 | 직접 수정하지 않음 |
| `.env` | 개인 환경의 실제 설정·비밀값 | 예시에서 필요한 값을 준비하고 Git에 포함하지 않음 |

`pnpm-lock.yaml`과 `uv.lock`도 도구가 생성하지만, 같은 의존성을 재현하기 위해 **Git에 포함하는 파일**입니다.

## 11. 권장 개발 순서와 확인 명령

처음부터 모든 빈 폴더를 채우기보다 **실제 상품 하나의 수집 → 저장 → API 조회 → 모바일 표시**를 먼저 연결합니다. 각 단계의 완료 기준은 [개발 마일스톤](최저가비교앱_개발_마일스톤.md)을 따릅니다.

| 순서 | 할 일 | 확인할 결과 |
|---|---|---|
| 1 | 서비스 범위·후보 쇼핑몰·비교 기준 정리 | 무엇을 어떤 조건으로 비교할지 설명할 수 있음 |
| 2 | Python으로 실제 데이터 확보 검증 | 같은 상품의 가격·옵션·배송비 정보를 비교할 수 있음 |
| 3 | DB 모델·API 데이터 규칙·Worker 저장 경로 결정 | 저장 형식과 요청·응답 형식이 정리됨 |
| 4 | 상품 하나의 저장과 API 조회 구현 | 저장한 상품을 API에서 조회할 수 있음 |
| 5 | 모바일 상품 상세에 실제 API 연결 | 수집한 실제 데이터가 화면에 표시됨 |
| 6 | 검색·관심 상품·가격 추이·알림 확장 | 각 기능의 정상·빈 결과·실패 동작을 확인함 |
| 7 | 랜딩·스토어 자료·출시 절차 준비 | 소개 페이지와 실제 서비스 상태가 일치함 |

명령은 저장소 루트에서 실행합니다. 최초 설치와 환경 변수 설정은 [SETUP.md](../SETUP.md)를 먼저 확인하세요.

| 목적 | 명령 | 범위 |
|---|---|---|
| JS 앱 함께 실행 | `pnpm dev` | 공유 패키지 빌드 후 모바일·API·랜딩 실행 |
| 모바일만 실행 | `pnpm dev:mobile` | 개별 실행 전 공유 패키지 빌드 필요 |
| API만 실행 | `pnpm dev:api` | 개별 실행 전 공유 패키지 빌드 필요 |
| 랜딩만 실행 | `pnpm dev:landing` | 소개 웹사이트 개발 서버 |
| Worker 실행 | `pnpm dev:crawler` | 현재 준비 상태 출력 후 종료 |
| 타입 검사 | `pnpm typecheck` | 모든 TypeScript 패키지 |
| 린트 | `pnpm lint` | 현재 ESLint가 구성된 랜딩 |
| 빌드 | `pnpm build` | API·공유 패키지·랜딩 및 모바일 웹 번들 |
| Prisma 스키마 검사 | `pnpm db:validate` | 스키마 유효성 확인 |
| Prisma 클라이언트 생성 | `pnpm db:generate` | DB 모델에 맞는 코드 생성 |
| shared 변경 반영 | `pnpm --filter @de-o/shared build` | 공통 코드·타입 다시 빌드 |
| DB 패키지 변경 반영 | `pnpm --filter @de-o/db build` | 클라이언트 생성 및 패키지 빌드 |

pnpm이 PATH에 없는 환경의 준비 절차와 npx/Corepack 호출 차이는 [SETUP.md](../SETUP.md)의 사전 준비를 따릅니다. 내부에서 pnpm을 다시 호출하는 스크립트까지 실행되는지 확인합니다. 모바일 웹 빌드 통과와 Android·iOS 실기기 검증은 별개이며, DB·실제 수집·알림의 동작도 해당 기능 구현 후 따로 확인합니다.
