# 최저가 비교 앱 개발 마일스톤

첫 번째 목표는 **같은 상품의 가격을 두 쇼핑몰에서 가져와, 같은 조건으로 비교할 수 있는지 확인하는 것**입니다. 기술 스택은 팀원이 작성한 `projects_architect.md`의 구조를 반영하고, 데이터 검증 결과에 따라 카테고리와 상세 기능을 확정합니다.

이 문서는 기존 개발 마일스톤에 팀의 아키텍처를 통합한 실행 계획입니다. **기술 스택과 서비스 구조는 확정 사항**, 상품 수·주차별 일정·A/B 역할 분담은 기존 계획안입니다. 인증 방식, 배포 플랫폼, 스타일링 방식, 대상 쇼핑몰, 상품 동일성 판별 기준은 아직 확정하지 않았습니다.

## 계획의 전제

- 팀 구성: 2명
- 작업 시간: 각자 주 15~20시간
- 목표 일정: 약 12주 내 첫 출시, 출시 후 1주간 초기 운영 검증
- 아래 기간은 계획용 추정이며, 제휴 승인 대기와 새로운 기술을 배우는 시간은 별도로 고려합니다.
- 각 단계의 완료 기준을 충족했을 때 다음 단계로 넘어갑니다.
- Next.js 소개 페이지 작업을 포함한 계획입니다. 핵심 기능은 모바일 앱에서 제공하며, 랜딩 페이지는 9~10주차에 제작합니다.
- M3 완료 시 실제 개발 속도와 배포 환경 준비 상태를 기준으로 남은 일정을 다시 산정합니다.

## 반영한 서비스 구조와 기술 스택

**React Native + Expo 모바일 앱을 중심으로 Express API와 MySQL·Prisma를 연결하고, 수집 작업은 Python Worker로 분리합니다. Next.js는 앱 소개용 랜딩 페이지로 사용합니다.**

| 영역 | 확정 기술 | 책임과 범위 |
|---|---|---|
| 모바일 앱 | React Native + Expo | 검색, 가격 조회·비교, 관심 상품, 차트, 알림 설정과 수신 등 실제 서비스 기능 |
| 백엔드 API | Express | 모바일 API, 요청 검증, 가격 비교 등 서버 측 비즈니스 로직 |
| 크롤러 | Python | 별도 Worker 프로세스에서 쇼핑몰별 수집 작업 실행 |
| 데이터베이스 | MySQL | 상품·판매 정보, 가격 이력, 알림 운영에 필요한 데이터 저장 |
| ORM 및 DB 스키마 관리 | Prisma | Express의 DB 접근과 공통 DB 스키마·마이그레이션 관리 |
| 소개 웹사이트 | Next.js | 앱 설명, 주요 기능 소개, 사용 영상, 다운로드 링크 |
| 모노레포 및 JS 패키지 관리 | pnpm workspace + Turborepo | 앱·API·랜딩·공유 패키지의 작업 및 의존 관계 관리 |

### 디렉터리별 개발 책임

| 경로 | 역할 | 의존 관계와 경계 |
|---|---|---|
| `apps/mobile` | Expo 모바일 앱 | `packages/shared`의 공통 계약을 사용하고 Express API를 호출 |
| `apps/api` | Express API 서버 | `packages/shared`와 `packages/db`를 사용 |
| `apps/crawler` | Python 크롤러·Worker | API 서버와 별도 프로세스로 실행. 수집 결과의 저장 경로는 M3에서 확정 |
| `apps/landing` | Next.js 앱 소개 페이지 | 핵심 비즈니스 로직과 분리. 가격 검색·비교 기능을 중복 구현하지 않음 |
| `packages/db` | Prisma 설정과 DB 스키마 | 스키마 변경과 마이그레이션을 한곳에서 관리. 모바일에 DB 접속 정보를 전달하지 않음 |
| `packages/shared` | 모바일과 API의 공통 계약 | 요청·응답 구조, 검증 스키마, 경로 정보 등 공유. DB 접속 정보와 서버 비밀키는 포함하지 않음 |
| 루트 설정 | `package.json`, `pnpm-workspace.yaml`, `turbo.json` | 공통 실행 명령과 JS 패키지 작업 순서 관리 |

### 실행 흐름과 프로세스 경계

- 모바일의 조회 흐름은 **Expo 앱 → Express API → Prisma → MySQL**입니다.
- Python Worker는 수집 작업을 별도로 실행합니다. 앱의 조회 요청을 처리하는 동안 여러 쇼핑몰을 즉시 순회하는 방식은 사용하지 않습니다.
- API와 Worker는 별도로 실행·재시작할 수 있어야 합니다. 수집 실패나 지연이 기존에 저장된 상품 조회까지 중단시키지 않도록 합니다.
- Next.js는 소개·영상·다운로드 안내를 담당하며, Express API를 Next.js Route Handler로 대체하지 않습니다.
- 모노레포의 핵심 목적은 모바일과 API의 공통 계약을 관리하는 것입니다. 웹과 모바일의 UI 공유는 필수 목표에 포함하지 않습니다.
- Python의 가상환경과 의존성 관리 도구는 별도로 정합니다. `pnpm workspace`를 사용하는 JS 영역과 Python 실행 환경을 각각 재현할 수 있도록 실행 절차를 기록합니다.
- Python 수집기는 기존 계획의 제휴 API 활용 가능성을 배제하지 않습니다. 실제 수집 방법은 쇼핑몰별 접근 권한과 이용 조건을 확인한 뒤 결정합니다.

### 구현 전에 결정할 항목

원문 아키텍처의 전체 그림에는 Worker에서 MySQL로 이어지는 경로가, 의존 관계에는 Worker에서 API 또는 데이터 저장 흐름으로 이어지는 경로가 표시되어 있습니다. **저장 방식은 확정된 것으로 간주하지 않고 M3에서 하나로 결정합니다.**

| 항목 | 현재 상태 | 결정 시점과 산출물 |
|---|---|---|
| 대상 카테고리·쇼핑몰 | 미정 | M1에서 후보 선정, M2에서 실제 데이터 확보 결과로 확정 |
| 동일 상품·가격 비교 기준 | 미정 | M1에서 모델·옵션·수량·배송비 처리 규칙 초안, M2 실제 데이터 검증 후 확정 |
| 사용자 인증·관심 상품 보관 방식 | 미정 | M1에서 회원가입·기기 간 동기화 범위 결정, M3에서 인증·저장 설계 확정 |
| Worker의 데이터 저장 경로 | 미정 | M3에서 내부 API 전달 또는 DB 직접 저장 중 선택하고 권한·검증·실패 처리 방식 문서화 |
| 배포 플랫폼 | 미정 | M3에서 API·Worker·MySQL·랜딩의 배포 위치, 비용, 비밀값 관리 방식 확정 |
| 스타일링 방식 | 미정 | M3에서 모바일·랜딩의 구현 방식 결정 |
| Python 환경·스케줄 실행 방식 | 미정 | M3에서 의존성 관리, 실행 주기, 중복 실행 방지와 재시도 방식 결정 |

저장 경로의 **계획상 우선 검토안**은 Python Worker가 수집 결과를 내부 API로 전달하고, Express가 검증한 뒤 Prisma를 통해 MySQL에 저장하는 방식입니다. 이는 팀 확정 사항이 아닙니다. 이 방식을 선택하면 Worker 요청 인증, 중복 저장 방지, 전송 실패 시 재시도가 필요합니다. DB 직접 저장을 선택하면 Python의 DB 접근 구현과 제한된 권한을 따로 마련하고, 스키마 변경은 `packages/db`의 마이그레이션에 맞춥니다.

## 1차 출시 범위

| 항목 | 1차 출시 범위 |
|---|---|
| 대상 상품 | 카테고리 1개, 관리 대상 상품 30~50개 |
| 비교 대상 | 데이터 이용 조건을 확인한 쇼핑몰 2곳 |
| 핵심 기능 | 등록 상품 검색, 가격 비교, 관심 상품 저장, 가격 추이, 목표 가격 알림 |
| 상품 연결 | 초기 상품은 팀이 검수해 연결하는 계획안. 구체적인 동일 상품 판별 규칙은 M1~M2에서 확정 |
| 가격 기준 | 동일 옵션의 상품 가격과 확인 가능한 배송비를 합산하는 계획안. 카드·개인별 쿠폰 할인은 별도 표시하며 상세 기준은 M1~M2에서 확정 |
| 사용자 계정 | 인증 방식은 미정. 기존의 회원가입 없는 기기 단위 이용은 범위 축소안으로 유지하고 M1에서 채택 여부 결정 |
| 지원 환경 | Android·iOS, 스마트폰·태블릿 기본 화면 대응 |
| 수익화 | 승인된 제휴 링크와 최소 광고 배치 |
| 소개 웹사이트 | Next.js로 앱 설명·기능 소개·사용 영상·다운로드 링크 제공 |

**어떤 상품끼리 비교하는가와 무엇을 가격으로 보는가를 기획 단계에서 결정해야 합니다.** 같은 상품명이라도 용량·수량·구성품이 다르면 잘못된 최저가가 나오기 때문입니다.

| **M3. 모노레포와 기본 연결 — 3주차** | pnpm workspace·Turborepo와 디렉터리 구성, Expo·Express 기본 연결, Prisma 스키마·마이그레이션 구성, shared 계약 작성. Worker 저장 경로·Python 환경·배포 위치·인증·스타일링 결정. 양쪽 OS 빌드·설치·시험 푸시 확인 | **실제 상품 1개의 수집→MySQL 저장→Express 조회→Expo 표시가 동작함.** 새 개발 환경에서 두 사람이 동일 절차로 실행·DB 구성을 재현함. M2 데이터를 보존하고 후속 일정을 재산정함 |
| **M4. 가격 비교 기반 완성 — 4~5주차** | Python Worker의 쇼핑몰별 수집·주기 실행·재시도 구현. 관리 상품 30~50개 확대. MySQL에 상품·판매 정보·가격 이력 구분 저장. Express 비교 API와 shared 요청·응답 계약 연결. 옵션·배송비·품절·오래된 가격 처리 | **7일간 자동 수집이 운영**되고, 표본 점검에서 상품·옵션 연결 오류가 없음. 수집 실패가 앱 조회를 막지 않으며, 중복 실행으로 가격 이력이 중복 저장되지 않음 |
| **M5. 핵심 모바일 기능 완성 — 6~7주차** | Expo 앱의 검색·결과 목록·상품 상세·관심 상품·차트·판매처 이동 구현. M3에서 정한 인증·보관 방식 적용. 로딩·빈 결과·통신 실패와 태블릿 화면 대응 | 사용자가 **검색→가격 확인→관심 상품 저장→추이 확인→판매처 이동**을 도움 없이 수행함. 재실행 후 관심 상품이 유지되고, 실제 저장된 가격 이력과 차트가 일치함 |
| **M6. 알림·수익화 완성 — 8주차** | 목표 가격·알림 설정 API와 Expo 화면 연결. 서버 측 판정·발송 작업의 실행 위치 확정 및 구현, 토큰 관리, 중복 발송 방지·알림 해제 처리. 제휴 링크·광고 적용 | 시험 환경의 가격 변화로 **Android·iOS 알림 수신과 상품 상세 이동**을 확인함. 중복 발송과 해제 후 발송이 없고 제휴 링크·광고가 정상 동작함 |
| **M7. 비공개 테스트와 랜딩 제작 — 9~10주차** | 실제 사용자 테스트와 가격 불일치·오알림·앱 종료 문제 수정. Next.js 랜딩에 앱 설명·기능·사용 영상·다운로드 영역 구현. 개인정보 고지·스토어 제출 자료 준비 | 핵심 오류가 해결되고 테스트 요건과 피드백·수정 기록이 확보됨. 랜딩이 모바일·데스크톱에서 표시되며, 미출시 스토어의 다운로드 상태를 정확히 안내함 |
| **M8. 심사·출시 — 11~12주차** | 프로덕션 액세스·앱 심사 신청과 대응. Express·Python Worker·MySQL·Next.js 배포와 오류 감시 확인. DB 백업·복구 절차 점검, 랜딩에 승인된 스토어 링크 반영 | **스토어 설치본의 검색·비교·저장·알림이 동작함.** API와 Worker를 개별 재시작할 수 있고 수집 실패를 확인할 수 있음. 랜딩 링크가 실제 앱 페이지로 연결됨 |
| **M9. 초기 운영 검증 — 출시 후 1주** | 수집 성공률, 가격 오류, 알림 중복·실패, API·Worker·DB·랜딩 운영비, 사용자 이탈 지점 확인 | 운영비가 정한 상한 안에 있고 주요 장애가 해결됨. 실제 사용 기록으로 다음 개선 항목을 결정함 |

## 데이터 검증과 일정상 주의사항

### 데이터 확보 검증

**M2가 이 프로젝트의 가장 중요한 통과 지점입니다.** 두 쇼핑몰의 비교 가능한 데이터를 확보하지 못하면 카테고리나 데이터 제공처를 다시 선택해야 합니다. API 가입만 완료하거나 임의 데이터를 화면에 표시한 상태는 M2 완료로 보지 않습니다.

가격 이력도 이때부터 축적합니다. 다만 **조회할 수 있다는 사실과 장기간 저장·재표시할 수 있다는 사실은 따로 확인**해야 합니다. 차트에는 실제로 확보한 기간만 표시하고, 수집 실패 구간을 가격 0원으로 저장하지 않도록 설계합니다.

M2는 수집 가능성을 확인하는 최소 검증 단계입니다. 저장용 필드와 형식을 기록해 두고 M3의 정식 스키마로 옮길 때 실제 가격 기록을 보존합니다. M3 이후 스키마 변경은 `packages/db`의 마이그레이션으로 관리합니다.

### Google Play 비공개 테스트 일정

개발자 계정과 테스터 확보는 1주차부터 병행합니다. 다만 기존 검토 노트의 일정 해석은 수정해야 합니다.

해당 Google Play 개인 계정의 **14일 요건은 계정 생성일부터 계산되지 않습니다. 비공개 테스트에서 최소 12명이 연속 14일 참여 상태를 유지해야** 프로덕션 액세스를 신청할 수 있으며, 이후 검토 시간이 추가됩니다. 따라서 11~12주차 출시는 심사 상황에 따라 밀릴 수 있습니다.

출처: [Google Play 공식 안내 — 새로운 개인 개발자 계정의 앱 테스트 요구사항](https://support.google.com/googleplay/android-developer/answer/14151465?hl=ko)

## 역할 분담

| 담당 | 주된 책임 |
|---|---|
| A | `apps/api`, `apps/crawler`, `packages/db` 중심. 데이터 제공처 조사, Python 수집, Express API, Prisma·MySQL, 가격 비교와 서버 알림 처리 |
| B | `apps/mobile`, `apps/landing` 중심. Expo 화면·검색·관심 상품·차트·푸시 수신, Next.js 소개 페이지, 기기별 테스트·스토어 제출 |
| 공동 | `packages/shared` 계약과 모노레포 규칙, 인증·저장 경로·배포 결정, 동일 상품 검수, 사용자 테스트, 운영 장애 대응 |

역할 분담은 계획안입니다. A에게 데이터·서버 작업이 집중되므로, M3에서 실제 작업량을 확인해 조정합니다. B는 랜딩 제작 전에 모바일 핵심 흐름과 실제 기기 동작을 우선 완료합니다.

## 첫 주 실행 항목

1. **대상 사용자와 구매 상황을 한 문장으로 작성합니다.** 누가, 어떤 상품을 살 때, 이 앱을 사용하는지 정합니다.
2. **카테고리 후보 2개에서 실제 상품을 각각 10개씩 고릅니다.** 모델·옵션을 구분하기 쉬운지 확인합니다.
3. **후보 쇼핑몰의 데이터 확보 가능성을 조사합니다.** 승인 필요 여부와 가격·배송비·이력 저장 조건을 표로 남깁니다.
4. **가격 비교 규칙 초안을 작성합니다.** 배송비 미확인, 다른 옵션, 품절, 오래된 가격을 각각 어떻게 처리할지 정하고 M2 데이터로 검증합니다.
5. **첫 출시 기능과 두 사람의 담당을 확정합니다.** 인증·동기화 범위, 주당 작업 시간과 월 운영비 상한도 함께 적습니다.
6. **팀원의 구조를 개발 기준으로 공유합니다.** 확정된 스택·디렉터리와 미정인 Worker 저장 경로·배포·스타일링을 구분하고, 미정 항목의 결정 담당자를 정합니다.

첫 주의 완료 결과는 **기획서 초안, 샘플 상품 목록, 데이터 제공처 검토표, 역할 분담표, 미정 설계 항목 목록**입니다. 첫 개발 작업은 그 결과를 바탕으로 **Python으로 상품 10개의 실제 가격을 가져와 저장하는 작은 검증 프로그램**부터 시작합니다. 해당 결과를 M3에서 Express·Prisma·MySQL·Expo 구조에 연결합니다.
